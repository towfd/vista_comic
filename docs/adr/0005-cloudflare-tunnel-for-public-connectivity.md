# Cloudflare Tunnel for a stable public endpoint

Status: accepted (2026-07-23), amended (2026-07-28) — Cloudflare Access with a Service Token is adopted in front of the tunnel, implemented and verified end-to-end (device off the home network, headers required); see `.scratch/remote-access/`.

For a stable, non-LAN-dependent way to reach the backend, a Cloudflare named Tunnel (the `cloudflared` daemon, bound to a subdomain of a Cloudflare-managed domain) was chosen over the alternatives: same-Wi-Fi LAN IP (only works at home), and Tailscale/WireGuard (a private mesh, viable but requires the tunnel client on every device rather than a plain public HTTPS URL). A named tunnel makes only an outbound connection from the host to Cloudflare's edge — no port-forwarding or static public IP needed — and HTTPS terminates at the edge, so the app needs no App Transport Security exception against it. `cloudflared` runs as a third `docker-compose.yml` service alongside `api` and `postgres`; only `api` gets an ingress route — `postgres` is never exposed through the tunnel, only over the internal Compose network / LAN localhost.

At the time of the original decision, no Cloudflare Access policy sat in front of the tunnel (single developer, own device, nothing sensitive reachable by URL alone). That "no Access" state has now been revisited and superseded: once the tunnel is genuinely reachable from anywhere, an unguarded URL is a real exposure. Cloudflare Access is configured on the public hostname, gated by a Service Token (`CF-Access-Client-Id` / `CF-Access-Client-Secret` headers) rather than an interactive login — the iOS app authenticates non-interactively by attaching these headers to every outgoing request, including image loads (`APIConfig.authorizedRequest`, shared by `APIComicRepository` and `AuthorizedAsyncImage`). Access enforcement happens entirely at Cloudflare's edge; the FastAPI application has no Access-related code and stays unaware of it.
