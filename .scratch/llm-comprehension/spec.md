# LLM-assisted comprehension: deeper explanation beyond literal translation

## Problem Statement

After M8, a reader can select a speech bubble, correct its OCR'd Vietnamese text, and get a literal translation they can save to 單字本. But a literal translation alone doesn't tell them *why* it's translated that way — it doesn't explain the sentence's grammar, why an ambiguous pronoun was resolved a particular way, or the tone of what was said. For a language learner, the bare translation is the easy part; the understanding is in the parts a plain translation leaves out. M8's own spec explicitly deferred this ("Word/sentence/context explanations and any LLM-assisted comprehension") to a future effort — this spec is that effort.

## Solution

Extend the existing "Translate" action on the OCR result screen (`CroppedSelectionPreview`) so it calls a cloud LLM (Claude) instead of only the on-device `Translator`. The cloud call receives the corrected selection text plus the crop and a downscaled full page image, and returns a structured result: a translation, grammar notes, context notes (how the surrounding panel/page resolved ambiguity), and tone/register notes. The existing on-device `Translator` (Apple's `Translation` framework) is kept, but demoted to an automatic fallback — used only when the cloud call fails or is declined, so translation still works without a hard failure. A persistent status banner at the top of the result screen tells the reader at a glance whether they're looking at a full cloud explanation, an offline/error fallback, or a content-declined fallback. Explanation content is saved to 單字本 alongside the translation, not discarded after viewing.

## User Stories

1. As a reader, I want grammar notes explaining the sentence structure of what I selected, so I understand how the words fit together, not just what they mean.
2. As a reader, I want context notes that reference what's visibly happening in the panel/page, so ambiguous references (e.g. a pronoun that depends on who's speaking to whom) are explained using the same visual cues I can see myself.
3. As a reader, I want tone/register notes, so I understand the emotional flavor and formality of the line, not just its literal content.
4. As a reader, I want the translation to still default to Traditional Chinese, matching M8's existing default, so most of the time I don't have to think about language selection at all.
5. As a reader, I want to still be able to change the target language for a specific translation, since M8 already gave me that flexibility and this feature shouldn't take it away.
6. As a reader, I want the deeper explanation to appear when I tap "Translate" — the same button I already use — not a separate new action, so the flow doesn't get more complicated.
7. As a reader, if I'm offline or the cloud service is unavailable, I still want to get a translation rather than a dead end, even if it's just literal.
8. As a reader, I want a clear, immediate visual signal — before I even read the content — of whether I'm looking at a full explanation or a degraded fallback translation, so I'm never confused about why the depth I expected isn't there.
9. As a reader, if the content is declined by the cloud service (rather than a connectivity problem), I want that communicated distinctly from "you're offline," so I don't waste time troubleshooting my network for no reason.
10. As a reader, I want to save the full explanation — not just the translation — to 單字本, so revisiting a saved entry later shows me everything I originally saw, not a stripped-down version.
11. As a reader, if a saved entry only has a translation (because it was saved from a fallback state), I want that to display sensibly, not as a broken or confusingly empty explanation section.
12. As a reader, I want whatever text I see and possibly corrected on the OCR result screen to be exactly what gets translated and explained, so my correction isn't silently discarded in favor of the cloud model's own reading of the image.
13. As a reader, if the default explanation feels shallow, I want a way to ask for a deeper one from a stronger model, so I'm not stuck with a weaker result when I actually need the detail.
14. As a reader, I want jumping back to a saved entry's source page (M8's existing "peek" feature) to keep working exactly as it does today, unaffected by this feature.
15. As the developer, I want the comprehension call to run only when the reader actually taps Translate, not automatically on every OCR recognition, so cost stays proportional to actual curiosity, not to how many panels exist.
16. As the developer, I want both the selection crop (full resolution) and a downscaled full-page image sent together, so the model has textual precision and coarse scene context without paying full-resolution image-token cost for context alone.
17. As the developer, I want the cloud comprehension capability behind its own protocol, distinct from `Translator`, so the already-shipped, reviewed OCR/translation code and its tests stay untouched, and the new capability is independently testable.
18. As the developer, I want the cloud provider's API key to live only in the backend's environment configuration, never in the iOS client, so it can't leak via a decompiled binary or network trace.
19. As the developer, I want a simple, global daily request cap on the backend, so a bug (e.g. a retry loop) can't generate unbounded cloud spend.
20. As the developer, I want a lenient per-request image-size ceiling on the backend, independent of the daily cap, so one oversized request can't blow up cost on its own.
21. As the developer, I want the backend response to distinguish "the model declined to analyze this" from "a network/server/rate-limit error," so the client can pick the right banner without guessing from an HTTP status code alone.
22. As the developer, I want explanation fields stored as additional columns on the existing saved-translation record, not a second, parallel storage concept, so "saved learning material" stays one coherent thing.
23. As the developer, I want zero behavior changes to `Translator`, `AppleTranslator`, `OCRRecognizer`, or `VisionOCRRecognizer`, since they're already shipped and reviewed — `Translator` only gains a new caller (the fallback path), not new behavior.
24. As the developer, I want the new protocol boundary tested with stubs, mirroring this codebase's existing test conventions (`OCRRecognizerTests`, `TranslatorTests`), so the test suite never depends on a real network call or a real API key.

## Implementation Decisions

- **New `Comprehender` protocol** (`Networking/`, mirrors `OCRRecognizer`/`Translator`'s shape): an async method taking the selection crop image, the full page image, the (possibly user-corrected) source text, and a target language, returning a structured `ComprehensionResult` (`translation`, `grammarNotes`, `contextNotes`, `toneRegister`) or throwing a `ComprehensionError` distinguishing at least a declined case from an underlying/network case.
- **`APIComprehender`**: the sole implementation, calling the backend's new `POST /comprehend`. Request carries the crop image (original resolution) and the full page image (downscaled to ~1024px long edge) as base64, the exact source text shown on screen (never re-derived from the image server-side — a user's OCR correction must be respected, not silently overridden by the model's own reading), and the target language code.
- **Response contract**: HTTP 200 with a `status` field discriminating `"ok"` (with the four result fields) from `"declined"`. Any other outcome — network failure, backend error, the daily cap, or the image-size ceiling — is a normal HTTP 4xx/5xx and surfaces as a thrown error on the client.
- **`CroppedSelectionPreview`'s "Translate" action** calls `Comprehender` first. On `.declined` or any thrown error, it falls back automatically to the existing `Translator` call (unchanged), and the UI tracks which of the three outcomes occurred so the correct banner renders.
- **Result screen gets a persistent status banner**, always the first thing shown once a result exists: ☁️ (blue) "雲端深度解釋" for a full success; 📱 (gray) "離線模式・僅逐字翻譯" for the offline/error fallback; ⚠️ (orange) "內容政策・僅提供翻譯" for the declined fallback. Below the banner, original text and translation are always shown; the grammar/context/tone sections render only when present (the success case).
- **A secondary action lets the reader re-request the explanation from the stronger model tier** (Claude Sonnet 5) if the default tier's (Claude Haiku 4.5) result is insufficient — the `/comprehend` request needs a way to carry the requested tier; the exact UI trigger/wording for this action is not locked here and is left to the implementer.
- **Backend**: new `POST /comprehend` endpoint, flat alongside the existing `/translations` (not nested under a comic/chapter path) — `/translations` keeps its existing save/list role unchanged; `/comprehend` is the new "get a result to show" step, mirroring M8's existing two-step "translate, then optionally save" flow. Validates both images against a lenient size ceiling before calling Claude, rejecting oversized requests with a 4xx. Enforces a global daily request-count cap (not per-user — no per-user identity exists in this backend, per `docs/adr/0005-cloudflare-tunnel-for-public-connectivity.md`) via a small Postgres table (`CREATE TABLE IF NOT EXISTS`, no migration tooling, mirroring `progress`/`saved_translation`'s existing precedent); cap value 300/day, purely an anomaly guard, not real usage-limiting. Calls the Claude Messages API with a `strict: true` tool-use schema enforcing the four result fields exactly; defaults to Claude Haiku 4.5, honoring a request override to Claude Sonnet 5 for the manual-upgrade path. The Claude API key lives only in the backend's gitignored `.env`, following `MANGA_LIBRARY_PATH`/`DATABASE_URL`'s existing pattern — never committed, never present in the iOS client.
- **`saved_translation` gains three new nullable columns**: `grammar_notes`, `context_notes`, `tone_register` (same `CREATE TABLE IF NOT EXISTS`-style addition as the table's existing columns, no migration tooling). `POST`/`GET /translations` are extended to accept/return these fields. No separate provenance/source column — a row with all three fields `NULL` already means "saved from a fallback state, translation only."
- **單字本's list** (`SavedTranslationRow` and related views) is extended to show the explanation fields when present (e.g. expandable), and renders unchanged when they're absent — no new empty-state design needed beyond what already exists for a translation-only row.
- No changes to `Translator`, `AppleTranslator`, `OCRRecognizer`, `VisionOCRRecognizer`, or any other already-shipped `ocr-recognition`/`ocr-translation` file's own behavior — this feature is additive; `Translator` gains a new caller, not new behavior.

## Testing Decisions

- Good tests exercise the `Comprehender` protocol boundary with stubs (success, declined, and thrown-error cases) — never a real Claude API call — mirroring `OCRRecognizerTests`'/`TranslatorTests`'s existing stub-based pattern in this codebase.
- Unit tests: a stub `Comprehender` proves the Translate-button flow renders the correct banner and content for each of the three outcomes, and correctly falls back to calling `Translator` on `.declined` or a thrown error.
- `APITranslationRepositoryTests` (existing file): extend to cover the three new optional fields round-tripping through save and list, using the existing stub pattern — no new protocol to test since `TranslationRepository` itself didn't change shape, only its payload.
- Backend: new tests for `/comprehend`'s request/response contract — the size-ceiling rejection, the daily-cap rejection, and the success/declined response shapes — stubbing or mocking the Claude API call rather than hitting the real Anthropic API from the test suite. Extend the existing `/translations` endpoint tests for the three new columns.
- `APIComprehender`'s real-world prompt/schema quality against actual Claude models is not automated (mirrors `VisionOCRRecognizer`'s and `AppleTranslator`'s existing stance that real-model accuracy isn't unit-testable) — it was already spot-checked manually during this feature's `/wayfinder` prototype (real Haiku 4.5 and Sonnet 5 calls against real manga content, see `.scratch/llm-comprehension/issues/06-schema-fields-and-model-tier-prototype.md`), and should be re-confirmed once real implementation code exists.
- Manual verification (required, environment permitting): select real Vietnamese text and confirm the cloud comprehension renders all four fields under the correct (blue) banner; force an offline or backend-error condition and confirm the fallback translation renders under the gray banner; confirm a saved entry with explanation content survives an app relaunch (proving backend persistence, not just local state), and that a fallback-only saved entry (no explanation) still renders sensibly in 單字本.

## Out of Scope

- Free-form, chat-style comprehension Q&A beyond the existing per-selection select → OCR → explain flow — this spec only extends M6/M8's existing interaction model.
- Batch/precompute processing of an entire chapter or comic at download time — considered and rejected during `/wayfinder` (see `.scratch/llm-comprehension/issues/01-destination-and-processing-timing.md`) in favor of staying real-time and proportional to what the reader actually selects.
- On-device (Apple Foundation Models framework) comprehension — ruled out because the reference device (iPhone 14 Plus) lacks the required A17 Pro chip; revisit only if the reference hardware changes.
- Verifying comprehension quality/reliability for target languages other than the default Vietnamese→Traditional Chinese path — accepted as an unverified assumption (see ticket 06), not tested here.
- Any translation entry point other than the OCR result screen (inherited, unchanged from M8's own scope).
- Cross-device sync, accounts, or any multi-user concept (inherited, unchanged from the rest of this backend).

## Further Notes

- Depends only on already-shipped work: M6 (`ocr-recognition`, the selection/crop UI and `OCRRecognizer` seam) and M8 (`ocr-translation`, the `Translator`/`TranslationRepository` seams, the `saved_translation` table, and 單字本).
- Per `.scratch/llm-comprehension/issues/07-claude-content-policy-for-manga-images.md`'s research, it's unconfirmed whether Claude Haiku 4.5 (the default tier) surfaces a structured refusal signal (`stop_reason: "refusal"`) the same way larger models do. The backend should treat "no valid tool-use result in the response" as sufficient to infer the declined case, rather than depending on a specific `stop_reason` value being present — confirm this empirically once real implementation code can call the live API.
- This spec was compiled from a fully-resolved `/wayfinder` map — see `.scratch/llm-comprehension/map.md` and its ten resolved decision tickets for the full discussion and reasoning behind each decision above.
