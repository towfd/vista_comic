# Comprehension response UX — wayfinder map

## Destination

A `spec.md` under `.scratch/comprehension-response-ux/`, ready to hand to `/to-tickets` — same shape as `.scratch/llm-comprehension/spec.md`. It reshapes M9's comprehension flow around two complaints: the reader waits too long for anything at all (the whole Translate action blocks on one slow cloud call), and the explanation comes back in an unpredictable language. The reader should get a literal translation immediately and let the deeper explanation arrive later, tracked in a new 歷史紀錄 (History) tab that replaces 單字本.

## Notes

- This map **modifies already-shipped M9 work** (`.scratch/llm-comprehension/spec.md`, merged as PR #35) rather than adding a new feature alongside it. Several of M9's own locked decisions are deliberately reversed here — most notably its "one Claude call produces both translation and explanation" merge and its manual Save/單字本 model. Read M9's spec and map before deciding anything, and say plainly in the spec which of its decisions this supersedes.
- Consult `/grilling` and `/domain-modeling` for open questions; `/prototype` for UI or model-output spikes needing a concrete artifact to react to.
- Standing constraint: single-user, single-device app (no accounts, no per-user identity — see `docs/adr/0005-cloudflare-tunnel-for-public-connectivity.md`). Keep solutions single-user-simple.
- Existing `saved_translation` rows are explicitly disposable — the developer has confirmed the data there is not worth preserving, so no migration path is needed for any storage decision on this map.
- The developer's stated end-goal (whole-book precompute, tap-a-bubble-for-instant-explanation) is **out of scope here on purpose** — this map exists to ship a usable version of the *current* interaction model first. Don't let decisions here quietly assume that future model.

## Decisions so far

- [Scope split and destination](issues/01-scope-split-and-destination.md) — of the three reported problems, the slow LLM response (1) and the explanation's language (3) form this map, whose destination is a `spec.md`; the OCR text-editing lag (2) is a separate `/diagnosing-bugs` effort, since it's a performance defect with an unknown root cause, not a decision to make.
- [Fast path is the on-device translator](issues/02-fast-path-on-device-translator.md) — the immediate result comes from the existing on-device `Translator`, promoted from "fallback on failure" to "always runs first"; the cloud `/comprehend` call then runs in the background and fills in the explanation. Splitting the backend into fast/slow endpoints and streaming the tool-use response were both considered and rejected.
- [Auto-record replaces manual save; 歷史紀錄 replaces 單字本](issues/03-auto-record-and-history-tab.md) — every Translate auto-creates a record, the manual "Save" button is removed entirely, and the 單字本 tab becomes a 歷史紀錄 tab in the same tab-bar slot (not a control in the reader, so its unread badge stays visible after the reader is dismissed).
- [Background lifecycle and manual retry](issues/04-background-lifecycle-and-retry.md) — **its lifecycle half was superseded by ticket 07** (the call is no longer client-owned, so nothing is ever abandoned); what survives and is now load-bearing is that no crop or page image is ever stored, because the page is re-derivable from the `comic_id`/`chapter_id`/`page_number` already on the record, and that a failed record keeps its translation and offers a manual retry.
- [Unread badge semantics](issues/05-unread-badge-semantics.md) — only a successfully-arrived explanation counts as unread (never the fast translation, never a failure); the count clears per entry when that entry is opened, not on visiting the tab; an explanation that lands while the reader is still watching the result screen is already-read.
- [Explanation language follows the target-language picker](issues/06-explanation-language.md) — `grammarNotes`/`contextNotes`/`toneRegister` are written in the same language the picker translates *to* (the reader's own language), so no second language control is introduced.
- [Background task ownership and observation](issues/07-background-task-ownership.md) — the explanation call leaves the app entirely: the backend owns it as a DB-backed queue drained by a lifespan worker (max 3 concurrent, FIFO, 120s per Claude attempt), so no app-level store is introduced and `pending` genuinely means "still running"; both screens observe by polling a backend that is the single source of truth, and the vanished "cancel on background" is replaced by reserving the daily cap at enqueue and refunding only when the request never reached Claude.
- [History record data model and API shape](issues/08-history-record-data-model.md) — `saved_translation` is dropped and rebuilt as `comprehension_record` (there is no Alembic, so `create_all` can add a table but never a column); one five-valued `status` column (`pending`/`running`/`ok`/`declined`/`failed`) is the sole discriminator and doubles as the worker's claim, recovered on restart by resetting `running` to `pending`; both translations are kept with the cloud one taking display precedence; `POST /comprehend` is removed in favour of six `/comprehensions` endpoints, and Pillow is added so the worker can downscale the page image the client no longer uploads.

- [Reader result screen states after the split](issues/09-reader-result-screen-states.md) — M9's verdict banner is deleted and its two jobs split: "is more coming" becomes a `深度解釋` section standing where the explanation will render, and "which translation is this" becomes a 📱/☁️ provenance chip on the translation column that explains the cloud-wins text swap where it happens; `pending` and `running` share one message while `declined` and `failed` stay distinct through copy and whether a retry button exists at all; and the Sonnet upgrade action is removed outright in favour of a model-tier picker chosen *before* translating, alongside the language picker, in the `UserDefaults` pattern this app already uses instead of a settings screen. Variants drawn in [Result screen variants](assets/09-result-screen-variants.md).

- [History tab list and detail UI](issues/10-history-tab-ui.md) — 歷史紀錄 is a flat, newest-first `List` of compact two-line rows (unread dot, source text, status glyph + comic/chapter + relative time) that push a detail screen reusing the result screen's vocabulary; opening the detail is what marks a record read, retry lives only there so it can't be spammed from the list, M8's peek-mode jump-back survives, and swipe-to-delete replaces the card's delete button while keeping its confirmation. Comic/chapter titles are joined server-side from the in-memory catalog rather than shown as the SHA-1 ids the record actually stores. Variants drawn in [History tab variants](assets/10-history-tab-variants.md).

- [Client-side removal and replacement boundary](issues/12-client-removal-boundary.md) — one `ComprehensionRepository` protocol replaces both `Comprehender` and `TranslationRepository`; `Features/Vocabulary/` and the M9 comprehension client are deleted outright while the on-device `Translator`, the OCR family, `ReaderRoute` and `LastUsedTargetLanguage` survive untouched (the last as the pattern ticket 09's model picker copies); `comprehendOrTranslateSelection` becomes a translate-then-enqueue function whose `.failed` means only that the *on-device* translation failed, with "translated but not recorded" modelled as a success variant; about 1,030 lines of tests are deleted as testing behaviour that ceases to exist.

- [Verify the explanation-language instruction against the real model](issues/11-verify-explanation-language-prompt.md) — live spike against real Vietnamese pages confirmed the diagnosis exactly (unmodified, the notes come back in *English* — the prompt's own language — while `translation` is unaffected because only its schema description names the target language) and settled the fix as one sentence appended to each of the three explanation fields' `description` in the tool schema, using the **bare BCP-47 code**, so no language-name mapping table has to be maintained and `_prompt_text` is untouched; Haiku 4.5 complied 18/18 note fields across 6 calls, and quoting the Vietnamese inline never dragged the surrounding prose out of Chinese.

## Not yet specified

- Volume over time. Every translate writes a record forever, with no pagination on `GET /comprehensions` and no archiving or pruning anywhere. The History tab (ticket 10) was expected to sharpen this and honestly did not: compact rows took a screen from ~2 records to ~10 and swipe-to-delete gave the reader a pruning tool, so both push the threshold further out without revealing where it is. A default row limit was considered there and rejected — without a "load more" it makes old records silently unreachable, which is worse than slow. Revisit with real row counts from real use, not a guess.

## Out of scope

- **Whole-book/whole-chapter precompute with tap-a-bubble instant display** — the developer's stated long-term direction (OCR + LLM over an entire manga at import time, stored in the backend, so no selection is needed at read time). It replaces this map's interaction model rather than extending it, and carries an unresolved cost question. Deliberately deferred to its own future `/wayfinder` effort so a usable version of the current model ships first.
- **The OCR text-editing lag** (tapping the recognized text to correct it stalls) — split out during charting into a separate `/diagnosing-bugs` effort; it's a defect needing root-cause diagnosis, with nothing to decide.
- **Converting the backend to async** — every route is a sync `def` running in Starlette's threadpool, and the developer raised moving the whole backend to `async def`. Deliberately not done here. The honest measurement is that it buys almost nothing at this scale: one user, a concurrency cap of 3 on the only long-running calls, and a default threadpool of 40, so the "threadpool contention" argument used while resolving [Background task ownership and observation](issues/07-background-task-ownership.md) does not actually bite — the real reason to cap concurrency is Claude spend, not threads. Half-converting would be *worse* than not converting: a sync DB call inside an `async def` blocks the event loop outright, so the change is all-or-nothing across `db.py` (`create_async_engine`/`AsyncSession`/`asyncpg`), the three store modules, all 14 routes, `comprehension_client` (`AsyncAnthropic`), and the `tests/conftest.py` engine fixture — roughly the whole 2,000-line backend, at the same time as this map's own large backend change. Revisit when real usage shows the backend actually being held up, with numbers rather than a hunch; a separate `/wayfinder` effort could reasonably take this and Alembic together.
- **Adopting Alembic** — the backend has no migration tool, so `create_all` can add a table but never a column, and every schema change costs a manual `DROP TABLE` (see [History record data model and API shape](issues/08-history-record-data-model.md)). Adopting Alembic is the right call, but it is infrastructure work rather than a step toward this map's spec, and writing a migration for a table this map is about to destroy anyway would be wasted. **The trigger is the moment this feature's schema lands and `comprehension_record` starts holding data worth keeping** — baseline the post-drop schema then, and every change after that is a migration. Note two things for whoever picks it up: `progress` already holds data that would hurt to lose (M8's continue-reading and jump-back), and `tests/conftest.py:78` builds the test schema through `init_engine`'s `create_all`, so adopting migrations without changing that fixture leaves tests validating a schema built by a different path than production's.
- **單字本 as a study/review feature** (spaced repetition, quizzing, curation) — the tab is being removed, not improved. The developer confirmed saved vocabulary is rarely revisited, which is the premise for replacing it with an automatic history.
