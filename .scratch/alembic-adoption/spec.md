# Adopt Alembic, and stop building the schema twice

## Problem Statement

This backend has no migration tool. `db.init_engine` calls `Base.metadata.create_all`, which issues `CREATE TABLE IF NOT EXISTS`: it adds a **new table** for free and will **never** add, drop or alter a column on an existing one.

So every schema change that is not a brand-new table is a manual step against the deployed Postgres, recorded by hand in `docs/manual-migrations.md`. M10 paid that cost once already — `DROP TABLE saved_translation` had to be sequenced by hand, after the rebuilt API was confirmed live, and the file spells out the failure mode if the ordering is got wrong: nothing fails loudly, `create_all` silently does nothing, and the symptom is a runtime "column does not exist" that reads like a code bug rather than a missed deploy step.

Adopting a tool was deliberately deferred, on an explicit condition: **the trigger is `comprehension_record` landing and starting to hold data worth keeping.** That has happened. `docs/manual-migrations.md` already records the trigger as fired.

## Solution

Alembic owns the schema. `create_all` is removed in the same change, the deployed database is baselined onto the initial migration, and the app runs `alembic upgrade head` itself on startup — so a schema change ships by rebuilding the container, with nothing to remember.

## Implementation Decisions

### Baseline by stamping, not by rebuilding

The deployed schema was compared against the models before writing this: `progress`, `comprehension_record` and `comprehend_usage` match exactly — same columns, nullability, primary keys, and no index declared in a model that is missing from the database. **There is no drift to reconcile.**

That fact is what makes stamping safe. The initial migration is autogenerated to create all three tables, and the deployed database — which already has them, with reading progress in `progress` that would hurt to lose — is marked as already at that revision with `alembic stamp head`.

**This is one last manual step**, which is mildly ironic for a change whose purpose is to delete manual steps. It is unavoidable: a database that already has the tables cannot run the migration that creates them, and it is one-time.

### `create_all` goes in the same change

Two mechanisms creating schema is strictly worse than one. `create_all` would silently create tables Alembic believes do not exist yet, and the two would drift with nothing to notice. So `init_engine` stops calling it the moment Alembic starts.

**That removal is what forces the test decision below** — it is not a separate choice.

### Tests migrate too

With `create_all` gone, `conftest`'s throwaway `vista_test` database has nothing to build it. It runs `alembic upgrade head` instead, once per session.

This closes a hazard both `docs/manual-migrations.md` and `ROADMAP.md` already flag: the test suite currently builds its schema through a different path than production's, so the suite validates a schema no deployment ever produces. After this, the schema under test is the schema that shipped.

### The app runs its own migrations, in-process

`alembic upgrade head` runs from the existing `lifespan` handler via Alembic's Python API — **not** from a shell entrypoint.

The reason is the failure policy below: a shell script cannot cleanly tell "the database is unreachable" from "the migration itself is broken", and `lifespan` already has exactly that distinction wired. Putting it in the entrypoint would mean rebuilding, in shell, a discrimination Python is already making.

Single uvicorn worker, so there is no second process to race for the migration lock.

### A failed migration and an unreachable database are different failures

- **The migration itself fails** (bad SQL, a conflict, a revision that will not apply): the container **fails hard** and does not serve. The schema is not what the code expects, and serving through that moves the error somewhere further away and harder to read.
- **The database is simply unreachable**: the existing behaviour stands — log it and serve the catalog anyway. Browsing comics never needed Postgres, and an outage should not take the library down.

This preserves the deliberate degrade-gracefully decision `lifespan` already carries, rather than reversing it wholesale, while refusing to extend it to a case it was never about.

### Autogenerate, then read it

Migrations are autogenerated and reviewed before landing, the standard practice at this scale. The review is not a formality: autogenerate does not reliably notice server defaults, type changes, or constraint renames.

### Configuration reads the URL from the app, not from `alembic.ini`

The database URL differs by context — `postgres` as the host inside the compose network, `localhost` from the developer's machine and from the test suite. `alembic/env.py` calls `config.get_database_url()`, the same function the app uses, rather than hardcoding a URL in `alembic.ini`.

`target_metadata` is `db.Base.metadata`, so autogenerate compares against the models the app actually uses.

## Testing Decisions

The suite's existing DB-backed fixtures keep their shape: a throwaway `vista_test`, the name guard requiring `_test`, and per-test truncation. Only how the schema gets created changes.

Worth covering:

- The initial migration applied to an empty database produces exactly what the models describe — the check that the baseline is honest, and the one that would have caught drift had there been any.
- `upgrade` then `downgrade` on the initial revision leaves a clean database, so the first migration is reversible rather than a one-way door.
- The suite runs green against a schema built by migration rather than by `create_all` — this is mostly a consequence, but a red suite here means the two paths disagreed, which is the whole hazard.

## Out of Scope

- **Backfilling migrations for the schema's history.** The baseline is the current state; how it got here lives in `docs/manual-migrations.md` and the git log. Reconstructing the M5→M10 sequence as migrations would be archaeology with no consumer.
- **A rollback runbook for the deployed database.** Downgrade is tested, but "what to do when a production migration goes wrong" is a procedure to write when there is a second person or a second environment. Today there is one of each.
- **Multi-worker or multi-replica migration locking.** One uvicorn worker, one container. Revisit if that stops being true.
- **Converting the backend to async**, which would change `env.py`'s engine handling. Still deferred, still waiting on numbers.
